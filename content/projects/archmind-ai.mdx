<Section n="01" id="overview" title="Overview" kicker="Problem · Context · What I built">

## Problem

Architecture review is a slow, senior-engineer-only bottleneck. Diagrams rot in
wikis. Risks go unnoticed until a production incident. Teams have no tooling
that evaluates a design across the tradeoffs it actually trades off, so a
scalable design and an insecure one get the same non-answer: *looks fine to
me* from whoever had ten minutes.

## Context

Three structural problems compound:

1. **Review is bottlenecked on seniority.** There are never enough staff
   engineers to read every design document, and most reviews happen as a
   rubber stamp after the decisions are already made.
2. **Architecture knowledge is static.** The diagram in the wiki is a
   photograph of a decision, not a live model. There is no way to ask *what
   breaks if this service fails?*
3. **Tradeoffs are invisible.** A design might be scalable but insecure, cheap
   but fragile. No one has tooling that scores across all the axes that
   matter at once.

## What I built

ArchMind AI is an **AI staff architect**. You upload a Mermaid or PlantUML
diagram, an image or PDF, or paste code, and it:

- **Runs seven analysis agents in parallel** — Scalability, Security,
  Reliability, Performance, Cost, Maintainability and Observability. Each
  scores one dimension and emits severity-ranked findings. The seven scores
  aggregate into a single architecture score.
- **Generates architectures from a description** — describe a system in
  natural language, get a Mermaid diagram, the stack rationale, and starter
  Kubernetes or Terraform manifests.
- **Simulates failure** — project p50/p95/p99 latency and cost across user
  tiers, then run a chaos simulator that traces cascade failure paths and
  estimates recovery time.
- **Re-optimises a design** against blueprints: cost-optimised,
  high-availability, enterprise-scale, multi-region — with side-by-side
  comparison against what you gave it.
- **Audits compliance readiness** against SOC 2, ISO 27001, GDPR, HIPAA and
  PCI DSS, and lists the outstanding gaps.
- **Answers questions about your own architecture** — *what happens if Redis
  fails?* — because the copilot is grounded in your parsed graph, not in
  general knowledge.
- **Audits infrastructure** — Terraform, Kubernetes YAML and Docker Compose
  for misconfiguration; OpenAPI specs for contract problems; database schemas
  for missing indexes.

</Section>

<Section n="02" id="system" title="System" kicker="Architecture · Data flow · Infrastructure">

## Architecture

A React + TypeScript frontend on Vercel talks to a FastAPI backend on Render.
Supabase provides JWT auth and PostgreSQL. Vercel and Render cannot hold
secrets for each other, so they talk in signed service tokens rather than
session cookies — that detail shaped most of the integration code.

The backend parses whatever you gave it into a **single unified graph
representation**: nodes for services, stores and clients, edges for calls,
with the protocol and any notes attached. Everything downstream operates on
that graph, not on the original file. Mermaid text is parsed directly; images
and PDFs go through vision extraction first.

Seven agents then run against that graph in parallel, each receiving the full
graph and its own scoring rubric. Findings are severity-ranked, deduplicated
across agents, and aggregated into a scored report.

<AgentLoopDiagram caption="The analysis loop. Seven specialised agents score independent dimensions of one parsed graph; the aggregator never lets an agent see another's output." />

## Data flow

Input → parse to graph → fan out to seven agents → deduplicate and rank
findings → aggregate to a score → persist to Supabase → stream the report to
the client, which can then branch into simulation, redesign or compliance
against the same graph.

## Infrastructure

Render's free tier spins down after roughly fifteen minutes idle, which meant
a forty-second cold start on the first request of a session. The fix is a
keep-warm workflow in GitHub Actions that pings the health endpoint every ten
minutes, plus client-side warming on page load.

</Section>

<Section n="03" id="engineering" title="Engineering" kicker="Decisions · Tradeoffs · Failures">

## Important decisions

**Seven specialists beat one generalist.** This was the central architectural
call. A single monolithic analysis prompt blends security reasoning into cost
reasoning into reliability reasoning and the result is mush. Each dimension
has genuinely different evaluation logic, so each gets its own agent with its
own rubric and its own severity scale. Architecture review is inherently
multi-agent for the same reason it is inherently senior-only: a security
engineer, an SRE and a cost analyst do not review a design the same way.

**Zero-config is a product decision, not a technical one.** The hard problem
was the LLM strategy. Requiring an API key before the product does anything
useful creates a chicken-and-egg problem: you cannot evaluate a tool you have
not configured. The answer was a provider fallback chain — Groq, NVIDIA,
OpenRouter, Gemini, Ollama, HuggingFace — and, when none of them are
configured, an eighteen-rule heuristic engine that produces a real baseline
score. No keys? The product still works. Add one provider and it upgrades
itself.

**Parse to one graph, not per-format pipelines.** Supporting Mermaid,
PlantUML, images and URLs as four separate code paths would have been four
times the surface area and four times the bugs. Parsing everything into one
graph means the agents, the simulator and the compliance auditor are written
once.

## Tradeoffs

- **Agent parallelism vs. latency and cost.** Seven agents is seven calls. They
  run in parallel so wall-clock stays acceptable, but the token cost of a full
  review is real. Bounding the findings each agent may return keeps it
  proportionate.
- **Render free tier vs. cold starts.** Paying for a warm instance was the
  obvious fix. The keep-warm workflow gets most of the benefit for the cost of
  a scheduled GitHub Action, at the price of occasionally pinging a service
  that might otherwise be asleep.
- **Heuristic baseline vs. honest scoring.** An eighteen-rule engine will never
  match a model. It is labelled as a baseline in the interface, and it exists
  so the product is never dead on arrival.

## Failures

Cold starts surfaced as an interface bug before they were understood as an
infrastructure bug — the first request after idle looked like a hang, and the
first instinct was to blame the frontend. Client-side warming fixed the
symptom; the scheduled keep-warm fixed the cause.

The provider chain had a subtler failure: a provider that returns malformed
JSON *and* a 200 status will silently pass a naive fallback check. Every
provider in the chain now validates shape before its result is accepted.

## Performance considerations

Graph parsing is the slowest synchronous step, so it is the one that had to be
fast. Agent fan-out is IO-bound and parallelises cleanly. Report streaming
keeps the perceived wait down even when the full review takes a while, because
the report is the artefact the user came for.

</Section>

<Section n="04" id="result" title="Result" kicker="What worked · What changed · What I learned">

## What worked

The multi-agent split is the reason the output feels considered. A design
that is fast and fragile and cheap gets three specific findings from three
different specialists, and the user can see which dimension each came from.
That specificity is what makes the report actionable.

The heuristic fallback changed the shape of the product more than any feature
did. Zero-config onboarding means the tool is usable in the first thirty
seconds.

## What changed

My assumption that the value was in the analysis. It is in the analysis being
*multi-dimensional and attributable*. A single score would have been easier to
build and much less useful.

## What I learned

- Seven specialised agents scoring independent dimensions produce better
  architecture insight than one monolithic analysis, every time.
- A heuristic fallback engine makes a product viable for anyone, and that is a
  product decision disguised as an engineering one.
- Architecture review is inherently multi-agent — for the same reason it is
  inherently senior-only.
- Cold starts are a UX problem wearing an infrastructure costume. Solve them
  at the interface layer first, then pay for the real fix.

</Section>
