<Section n="01" id="overview" title="Overview" kicker="Problem · Context · What I built">

## Problem

Every engineer runs the same broken setup. Notes live in one app, tasks in
another, project docs in a third, and the part that actually matters — the
*why* behind a decision — is scattered across all of them. Context dies in
the gaps between tabs, and nobody can reconstruct a past decision six weeks
later.

## Context

I started EngineerOS from a clean assumption: **the problem is storage.** Put
notes, tasks and docs into one database with one schema, ship a decent
interface on top, and the fragmentation disappears.

That assumption survived about two weeks of real use, and then it broke in
three specific places.

**Keyword search was useless.** The first version used plain SQL `ILIKE`.
Users search by meaning, not by exact words — someone types *how did I handle
rate limits* and the note that answers it is called *throttling middleware*.
Keyword search returns nothing. From the user's side the workspace looks
empty even though the answer is sitting right there. Fragmentation solved,
discovery still broken.

**The assistant hallucinated confidently.** The moment an LLM sat on top of
the corpus it started inventing answers that sounded right and were wrong.
For a workspace people trust with real decisions, a confident wrong answer is
worse than no answer at all — it erodes trust in the whole product on the
first bad response.

**Local-first felt great until search needed the server.** I wanted the snappy,
offline-tolerant feel of a local-first notes app. But semantic search and the
assistant both need server-side compute and the vector index. Naively
threading every interaction through the network turned the "snappy" app into
molasses.

## What I built

EngineerOS is a workspace where notes, tasks and projects are not three
tables in isolation but nodes in one graph, and where the retrieval layer is
semantic by default.

The knowledge graph is the part that matters. Notes, tasks and projects carry
real edges between them, so the assistant can traverse relationships — *this
task came from that decision* — instead of treating every record as an
island. Combined with HNSW retrieval, that means the system answers
"what did I decide about auth last month, and why" as a path through the
graph rather than a keyword match.

The one constraint that changed the product: **no source, no claim.** The
assistant answers only from retrieved workspace chunks and attaches the
originating note to every statement. That single rule turned it from
something that lies into something people rely on.

</Section>

<Section n="02" id="system" title="System" kicker="Architecture · Data flow · Infrastructure">

## Architecture

The stack is deliberately boring at the edges and opinionated in the middle.

- **Next.js 14 App Router with React Server Components** — the interface
  shell and all reads render on the server, where the data and the vector
  index already live. Search never pays a client round-trip per keystroke.
  Only editing stays client-side, to keep the local-first feel.
- **Supabase — PostgreSQL + pgvector** — one store for auth, the relational
  workspace, *and* the embeddings. Keeping vectors in the same database as
  the rows they describe means retrieval can be filtered by relationship in
  the same query that does the similarity search.
- **pgvector HNSW** — the index behind semantic search. Sub-200ms p95.
- **LangGraph** — multi-agent orchestration for task workflows, with state
  checkpoints so a multi-step run is recoverable instead of restarting from
  zero on any failure.
- **User-owned Supabase** — your data lives in *your* Supabase project, not my
  black box. For a tool that holds your thinking, ownership is a feature, not
  a footnote.

## Data flow

Writing a note embeds it and writes the row and the vector in one transaction.
Searching runs a single HNSW query that returns both the vector neighbours and
their relational rows. Asking the assistant runs that same retrieval, hands the
chunks to the agent graph, and streams back an answer where every sentence
carries the id of the note it came from.

<Section n="03" id="engineering" title="Engineering" kicker="Decisions · Tradeoffs · Failures">

## Important decisions

**Server-rendered shell, local editing.** The resolution to the third failure
was not choosing between local-first and server-side. It was drawing the line:
edits are local and instant, intelligence is server-side. That gives the snappy
feel where it matters and the accuracy where it counts.

**One store for rows and vectors.** Splitting the relational store from the
vector store would have been architecturally tidier and operationally worse —
two systems to keep consistent, and no way to filter a similarity search by
relationship in a single query. The knowledge graph only pays off because the
edges and the embeddings are co-located.

**Checkpointed agent steps.** Multi-step LLM workflows can silently multiply a
token bill. Bounded step counts plus persisted checkpoints make both the cost
and the failure mode predictable.

## Tradeoffs

- **Local-first UX vs. server-side intelligence.** Neither alone works. Edits
  local, intelligence remote, and the interface has to make that seam
  invisible or it feels broken.
- **Trust vs. helpfulness.** An assistant that says *I don't have a note on
  that* is less impressive in a demo and more useful in practice. Citations
  and provenance are what make it safe to rely on.
- **User-owned storage vs. operational simplicity.** Handing users their own
  database removes a whole class of my problem and adds a support burden. It
  was still the right call for a workspace that holds real thinking.

## Failures

The three failures listed in the overview were the substantive ones. The one
worth naming separately: for the first two weeks the product appeared to work.
Every feature was present, every demo looked fine. The breakage only appeared
when real people put their real, inconsistently-worded content into it. Unit
tests passed the whole time.

## Performance considerations

The expensive path is search, and the only thing that matters is the round
trip. Reads render on the server so the first meaningful paint already
contains results — there is no client fetch for the initial list. Editing is
optimistic and never waits on the network. The vector index is HNSW, which
keeps p95 under 200ms at the corpus sizes real users generate.

</Section>

<Section n="04" id="result" title="Result" kicker="What worked · What changed · What I learned">

## What worked

Semantic search found things keyword search could not. The *how did I handle
rate limits* → *throttling middleware* case stopped being a support question
and became an ordinary one. And the citation rule worked well enough that
people stopped checking the sources — which is the actual test of whether
provenance is doing its job.

## What changed

The assumption that storage was the problem. I had planned for a unified data
model and a nice interface. What actually shipped was a retrieval layer with
provenance, which is a different product.

## What I learned

Unifying storage is easy and mostly worthless on its own. Unifying *context* is
the product — meaning-based retrieval and explicit provenance are what make a
workspace feel connected rather than merely co-located.

The number I care about is not the 200ms. It is that **10+ people now use it
daily and lean on it hard.** A workspace only proves itself when people trust
it with the thinking they cannot afford to lose.

</Section>
