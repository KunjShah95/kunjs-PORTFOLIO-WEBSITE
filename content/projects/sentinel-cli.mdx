<Section n="01" id="overview" title="Overview" kicker="Problem · Context · What I built">

## Problem

Security auditing means running a dozen tools, each with its own flags, its own
output format, its own idea of severity, and its own idea of which file is
worth analysing. Then you correlate the results by hand, which is the part
nobody wants and everybody does.

## Context

The cost is not the tool invocations. It is the correlation. Thirteen tools
reporting the same issue in thirteen vocabularies is one finding, and a human
doing that reconciliation is the bottleneck in every audit I have watched.

## What I built

A single command that runs 13+ security analysers and produces one report.

- **Pluggable analyser architecture** — each security tool is a pipeline stage
  behind a common interface. Adding a tool means writing one stage, not
  rewriting the runner.
- **Normalised result schema** — every analyser maps into one shape, so
  cross-tool correlation is a query rather than a research project.
- **Cross-tool correlation** — the same file, line and rule reported by several
  tools becomes one finding with multiple sources, which is where most of the
  false-positive reduction comes from.
- **LLM-written summary** — findings explained in plain language for people who
  are not security engineers.

<Section n="02" id="system" title="System" kicker="Architecture · Data flow · Infrastructure">

## Architecture

Node and TypeScript, with each analyser containerised so a tool with a hostile
dependency graph cannot affect the runner. The LLM summary is a final stage
over the normalised findings, never an input to detection.

## Data flow

Target → analyser fan-out (containerised, isolated) → each maps to the common
schema → correlation pass merges findings that share file, line and rule →
severity reconciliation → LLM summary over the merged set → single report.

## Infrastructure

Docker for analyser isolation. The report is a static artefact — deliberately
not a service, because an audit tool that needs a running backend is an audit
tool that cannot run in the environment where you need it.

</Section>

<Section n="03" id="engineering" title="Engineering" kicker="Decisions · Tradeoffs · Failures">

## Important decisions

**Normalise before correlating.** The obvious design correlates raw tool output.
It does not work, because the tools disagree about what a finding even is.
Normalising into one schema first makes correlation a deterministic operation
and lets it run in the same pass as the merge.

**The LLM writes prose, it does not detect.** Detection is deterministic
tooling. The model explains already-correlated findings. Letting a model
decide what counts as a vulnerability reintroduces exactly the
unfalsifiable-output problem that made the original workflow painful.

**Containerise each analyser.** A tool with a native dependency that needs
libssl 1.0 does not get to break the runner.

## Tradeoffs

- **Schema richness vs. tool portability.** A richer common schema supports
  better correlation and requires more work per analyser. A thin schema is easy
  to adopt and correlates badly.
- **LLM summary vs. determinism.** A written summary is far more useful to a
  non-specialist and is non-deterministic. Keeping it strictly downstream of
  detection makes that acceptable.
- **Isolation overhead vs. safety.** Container-per-analyser costs startup time
  on every run and removes a whole category of failure.

## Failures

Early correlation merged findings on file alone, which meant one line with two
genuinely different problems became one finding and one of them disappeared.
Requiring line and rule as well as file to match fixed it, and cut false
positives by roughly 40% as a side effect.

</Section>

<Section n="04" id="result" title="Result" kicker="What worked · What changed · What I learned">

## What worked

Thirteen-plus tools behind one command, 70% less audit overhead, and about 40%
fewer false positives purely from correlating properly. The unified schema is
what made the last number possible.

## What changed

The premise. This began as a convenience wrapper and became a correlation
engine, which is the part that actually saves time.

## What I learned

- A unified CLI dramatically lowers the adoption barrier for security auditing.
  The people who need it most are the least willing to learn thirteen tools.
- Correlation is where the value is. Consolidation is table stakes.
- LLM-summarised reports make security findings legible to people who are not
  security engineers, which is most of the people who need to act on them.

</Section>
