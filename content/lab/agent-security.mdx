## What I was testing

Prompt injection against an agent is normally discussed as an arms race:
someone finds a phrasing that works, a vendor patches it, someone else finds
another. That is a losing shape for the defender, because the defender has to
know the specific phrasing.

The alternative is to treat it as a regression class. If *goal hijack* is a
named, testable property, then a change that reintroduces it is a test failure
rather than a disclosure.

## Method

Contributed to OWASP's Agent-Security-Regression-Harness: a security regression
workflow in CI, plus a scenario for the case that concerned me most — an agent
holding a legitimate goal and an API key, where injected content tries to
redirect the goal to exfiltrating the key.

The distinction that makes it testable: the agent is *not* jailbroken. It is
doing exactly what it was asked, on instructions it was given. There is no
bypass to patch, only a property to assert.

## Result

Merged. The scenario is now part of a standing suite rather than an issue
report, which means a future change to tool permissions or output handling
shows up as a red build instead of an incident.

The broader value was confirming that the useful contribution to a security
project is frequently a *test*, not a fix. Fixes get debated; a failing test
gets merged and then argues on its own.

## Still open

The hard open problem in agent security is not injection into a single turn.
It is gradual drift across a long-running goal, where no single step is
exploitable and the trajectory is not. That does not have a regression test yet.
