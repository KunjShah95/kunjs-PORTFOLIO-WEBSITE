I built a vector database from zero dependencies. Nine ANN algorithms. A
cost-based query planner. A crash-durable WAL. GPU acceleration. Six SDKs. Here
is what I built, why, and what I learned.

## Why build a vector database from scratch?

Every modern AI application needs vector search — RAG pipelines, semantic
caching, multimodal search, recommendations. The existing options (Pinecone,
Weaviate, Qdrant, Chroma) are excellent but opaque. I wanted to know exactly
how they work under the hood, and the only way to find out is to build one.

The goal was never to compete with production databases. It was to build
something complete and educational that demonstrates every major algorithm and
engineering decision in the space.

## Five layers

1. **Storage engine** — vector and metadata persistence with WAL crash
   durability
2. **Index layer** — nine ANN algorithms with automatic index selection
3. **Query planner** — cost-based optimisation across index types and filter
   predicates
4. **Ingestion pipeline** — multimodal text, image and audio with CLIP
   embeddings
5. **API layer** — Python, TypeScript, Go, Rust, Java and a CLI

## The nine algorithms

Each of these is a different point in the recall / build-time / memory
trade-off space:

| Algorithm | Recall | Index build | Query | Memory |
|---|---|---|---|---|
| **HNSW** | 99.2% | Slow | Fastest | High |
| **IVF + HNSW** | 97.8% | Medium | Fast | Medium-high |
| **SCANN** | 96.3% | Slow | Fast | Medium |
| **IVF** | 94.1% | Fast | Fast | Medium |
| **IVF + PQ** | 91.5% | Fast | Fast | Low |
| **NSW** | 92.7% | Medium | Medium | Medium |
| **Annoy** | 90.8% | Fast | Fast | Medium |
| **KD-Tree** | 87.4% | Fast | Fast (low-D) | Low |
| **Brute force** | 100% | — | Slowest | n/a |

HNSW is the crown jewel: consistently above 99% recall with sub-millisecond
queries at million scale, using multi-layer graph navigation with a
controllable `efConstruction` that trades build time for search quality.

It also costs the most memory and takes the longest to build. That is the
trade, and it is usually worth it.

## The crash-durable write-ahead log

The hardest engineering problem in the whole system was not the index. It was
crash safety.

- **fsync-guaranteed persistence** — every write is flushed before
  acknowledgement
- **Append-only segments** with periodic compaction, so the log cannot grow
  without bound
- **Checksummed entries** for corruption detection during recovery
- **Point-in-time recovery** — replay from the last checkpoint to restore
  state exactly

The cost is write latency: synchronous fsync adds roughly 5–15ms per write on a
standard SSD. For workloads that can tolerate less durability the WAL mode is
configurable — fsync per write, per batch, or async.

## The cost-based query planner

Multiple index types means the system has to choose correctly per query. The
planner estimates the execution cost of each candidate index given:

- Query vector dimensionality
- Current dataset size
- Filter predicate selectivity, estimated from histogram statistics
- Required recall, configurable per query
- Available memory budget

It picks the lowest estimated cost and falls back to brute force when no index
meets the recall requirement. Against an exhaustive sweep it selects the optimal
index about 94% of the time.

## Multimodal ingestion

A vector database is only as good as its embeddings. The pipeline handles:

- **Text** — sentence-transformers, OpenAI and custom BERT, with chunking
  strategies
- **Images** — CLIP embeddings with automatic preprocessing
- **Audio** — Wav2Vec2 and Whisper embeddings for speech and music
- **Hybrid search** — dense vector similarity combined with sparse BM25
  retrieval

All embeddings are normalised to unit vectors, batched for throughput, and
stored with metadata for filtered search.

## GPU-accelerated indexing

Index construction is the most expensive operation in the system — HNSW on 10M
vectors can take hours on CPU. I implemented GPU index build with CuPy and
custom CUDA kernels:

- CuPy-based distance matrix computation, 50–100x faster than NumPy on large
  batches
- Custom CUDA kernels for HNSW graph construction, parallelising neighbour
  selection and edge pruning
- SIMD-optimised distance functions for cosine, dot product, L2 and inner
  product using AVX2/AVX-512 intrinsics

On a single A100, GPU-accelerated HNSW build completes 10M vectors in about 12
minutes against roughly 8 hours on a 32-core CPU — a 40x speedup.

## Six SDKs and deployment

- **Python** — reference implementation, full API coverage, NumPy and Pandas
  interop
- **TypeScript** — browser-compatible and Node, with streaming
- **Go** — goroutine-based concurrent client with connection pooling
- **Rust** — zero-copy serialisation with Arrow Flight interop
- **Java** — reactive streaming client over gRPC
- **CLI** — full command line with JSON/CSV import and export

Deployment options: embedded in-process, a standalone server with gRPC/REST, or
Kubernetes-native with Helm charts and Terraform modules.

## What I learned

1. **HNSW is the king of ANN** — nothing else delivers 99%+ recall at
   sub-millisecond latency at million scale, at the cost of memory and build
   time.
2. **Crash durability is 80% of the engineering.** Index logic is
   straightforward. Surviving a power failure at any point is where the real
   complexity lives.
3. **Query planning matters more as index count grows.** With nine index types
   and varying data distributions, the planner saves users from understanding
   the internals.
4. **GPU acceleration is transformative for index build.** 40x changes the
   relationship with iteration from *build overnight* to *build during lunch*.
5. **SDK ergonomics determine adoption.** No matter how good the database is,
   if the Python SDK is awkward, nobody will use it.

**Building from scratch is the best way to understand. And understanding is the
best way to build better.**
